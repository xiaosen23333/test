## 三、屏幕上会看到什么（这次是重点）

这一版加了**诊断通道**。左边那行字分三段：

```
帧循环运行中，第 300 帧                          ← ① 人话状态
客体 3/5 调用 nninitStartup | 录 1200 放 1180 丢 0 | 本帧 pass 1 draw 0 present 0   ← ② 一行总览
—— 上次运行的最后几行 ——                        ← ③ 上次运行的日志尾部
[客体] 第 3 步：调用 nninitStartup
```

### 可能的几种情况

| 屏幕显示 | 含义 | 下一步 |
|---|---|---|
| ① 一直停在 `正在装载游戏模块…` | 卡在装载 | ② 会给出卡在哪个模块 |
| ① 显示 `装载失败 rc=-10-i` | 第 i 个模块装载失败 | 按 i 定位 |
| ① `已装载。等待启动序列…` 不动、② 帧数不涨 | 宿主起来了，但帧循环没跑 | 看帧循环 |
| ① 帧数在涨、② `draw 0 present 0` | 帧循环正常，客体没到渲染 | 图形层还是空的（预期） |
| ① 帧数在涨、② `draw > 0` 但**画面全黑** | 命令录到了，Metal 层没画出来 | 就是 `hle_nvn_mtl_apply.m` 那 3 个 TODO |
| **App 直接消失（闪退）** | 客体崩了 | **见下：再打开一次 App** |

### 闪退了怎么办（这次不用连电脑）

**再打开一次 App**，屏幕第三段会显示**上次运行**日志的最后几行 ——
里面写着客体五步走到了哪一步（`[客体] 第 N 步：…`），最后一行就是崩的地方。

原始日志也在：**文件 App → 我的 iPad → DmGame → dm-log.txt**（要的话发我）。

## 四、为什么加了这个诊断通道

客体（游戏）是**跑在主线程上**的（帧循环 → 进客体 → `nnMain`）。
它一旦不返回，主线程就被它占住 —— **屏幕上的字再也不会更新**。
也就是说「只看屏幕」这条路的上限很低：它只能告诉你「进客体之前」发生了什么。

所以这一轮把「走到哪一步」改成**写文件**（每条立刻落盘），
并在下次启动时把文件尾部**显示到屏幕上**。这样：
一次装机，就能回答「卡在哪一步 / 崩在哪一步」。

具体打了哪些标记见 `work/porting/交接文档.md` 的第四节。
