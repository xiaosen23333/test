## 二、本轮定位到的两个错（都是确定的，不是猜的）

### 错 1：客体的 4 个线程槽从来没被填过

改写器把客体所有线程相关访问都改成「读宿主线程槽」：

```
mrs x18, tpidrro_el0   →  x18 = *(宿主tpidrro_el0 + 键号K18×8)
mrs/msr tpidr_el0      →  ……               键号KTLS×8
mrs tpidrro_el0        →  ……               键号KTLR×8
（svc / 读 cntpct 从 KGATE 槽取门地址）
```

**槽里必须放指针，而且必须宿主来放**。全仓库搜索：**从来没有任何地方填过**
（只有 `hle_nn_thread.c` 里给 nn::os 线程簿记用的 `tls_set`，用的是另一批键）。
→ 客体第一次用 x18/tpidr_el0 读到 NULL → `ldr w0,[NULL,#8]` → SIGSEGV。
**这与「崩在第 1 步」完全吻合**（第 1 步 `_init`/`_init_libc1` 是 libc 初始化，一上来就碰 TLS）。

### 错 2：TLSDESC 的 resolver 被填成 0 —— 而客体**真的会 `blr` 它**

上一版 loader.c：`((uint64_t *)where)[0] = 0;`，注释还写「resolver 已不需要」。**错的**。
从**解压后的模块**反汇编出来的实际指令（work/porting/tls_probe.py 的证据）：

```
adrp x0, <描述符页>
ldr  x1, [x0, #lo12]     ; x1 = desc[0] = resolver = 0
add  x0, x0, #lo12       ; x0 = &desc[0]   ← 入参是描述符地址
blr  x1                  ; ⇒ blr 0 ⇒ 立刻崩
mrs  x8, tpidr_el0
strb w20, [x8, x0]
```

现在填真 resolver：`uint64_t dm_tlsdesc_resolver(uint64_t *desc) { return desc[1]; }`。
`tlsdesc_selftest` 现在**真的跑一遍重定位再核对**：62/62 条 resolver 与偏移都对。

## 五、顺带修掉的一个「假绿灯」（重要）

本机 `vcvars64.bat` 要查注册表，受限环境下 `reg.exe` 被拦 → `INCLUDE/LIB` 没设上 →
每个源文件报 `C1083: stddef.h` → 编译失败；而 `build_all.ps1` 原来只看「exe 在不在」，
**旧 exe 被当成编译成功**，17 项自测全绿。**我一开始也被这个假绿灯骗了一次**
（对照 exe 时间戳才发现是 01:10 的旧二进制）。
现在：编译前先删旧 exe + 额外查编译日志里的 error；`dm_env.ps1` 加了按标准路径直接
填 `INCLUDE/LIB` 的兜底。改完重跑：**17/17 是真通过**。
